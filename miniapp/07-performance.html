📇 术语卡 ​

术语白话解释
setData把数据从逻辑层送到渲染层的「搬运工」，搬得越多越频繁就越卡
逻辑层 / 渲染层小程序的两个世界：JS 在逻辑层跑，页面在渲染层画，中间靠 setData 传话
按需注入启动时只加载当前页面用到的组件代码，而不是全部
代码压缩上传时去掉空格注释、缩短变量名，让包更小（minified）
WebP一种比 JPG/PNG 更小的图片格式，同画质体积常常省一半
懒加载图片滚到屏幕附近才加载，首屏不再一次性下载所有图
体验评分开发者工具里的自动体检工具，按官方最佳实践给页面打分

🐢 setData：最容易踩的性能黑洞 ​

回顾第 2 章：setData 是逻辑层和渲染层之间唯一的数据通道，每次调用都要把数据序列化后跨层传输。慢的根源就三个：

  1. 调用太频繁：比如在滚动事件里每秒 setData 几十次
  2. 一次传太多：把整个大对象丢过去，实际只改了一个字段
  3. 传了不该传的：把纯逻辑数据（不用渲染的）也塞进 data

三个优化手段，一一对照：

手段一：合并调用。多次 setData 合成一次：

js
// ❌ 改前：两次跨层传输
this.setData({ a: 1 })
this.setData({ b: 2 })

// ✅ 改后：一次搞定
this.setData({ a: 1, b: 2 })

手段二：传路径，精准更新。只想改列表第 2 项的名字时，别把整个 list 重新传一遍：

js
// ❌ 改前：整个数组重新序列化传输
const list = this.data.list
list[2].name = '新名字'
this.setData({ list })

// ✅ 改后：只传这一个字段
this.setData({ 'list[2].name': '新名字' })

手段三：高频场景做节流。滚动、输入框这类高频事件，先判断「值得更新吗」：

js
// ✅ 页面滚动：变化超过 50px 才更新一次
onPageScroll(e) {
  if (Math.abs(e.scrollTop - (this._last || 0)) < 50) return
  this._last = e.scrollTop
  this.setData({ scrollTop: e.scrollTop })
}

注意

非渲染数据不要放 data！比如计时器的 id、临时计算结果，直接挂 this._timer 这种自定义属性就行。放 data 里，每次 setData 都白白背着一堆用不上的数据传输。

✅ 你应该看到： 在滚动页面时打开调试器「AppData」面板，scrollTop 只以约 50px 的步进变化，而不是每滚动 1px 就刷新一次；滑动明显更顺滑。

📦 包体积优化与代码质量 ​

小程序对包体积有硬性限制：主包和单个分包都不能超过 2M 左右，所有分包总量也有上限（具体数字以官方文档为准）。超了就传不上去。四个瘦身手段：

  1. 开启压缩上传：示例工程已经配好了，看这两项——es6（ES6 转 ES5）、minified（压缩代码），上传时自动生效
  2. 图片搬家：本地图片是体积杀手，一张没压缩的照片就好几 MB。把它们传到 CDN 或云存储（第 8 章），代码里只放 URL
  3. 清理无用代码：删掉不再用的页面、组件、console.log 大量输出的调试文件，用「代码依赖分析」（工具菜单 → 工具 → 代码依赖分析）找出死代码
  4. 用好分包：第 5 章学过，把低频页面（如设置、关于）放进分包，主包只留核心路径
json
// 引自示例工程：examples/native-demo/project.config.json（节选）
{
  "compileType": "miniprogram",
  "appid": "touristappid",
  "projectname": "native-demo",
  "setting": {
    "es6": true,
    "postcss": true,
    "minified": true,
    "urlCheck": false
  },
  "condition": {}
}

⚡ lazyCodeLoading：按需注入 ​

默认情况下，小程序启动时会把所有自定义组件的代码全部注入，哪怕这个页面只用到其中一个。配置一行，就能改成「用到谁注入谁」：

json
// 引自示例工程：examples/native-demo/app.json（完整文件）
{
  "pages": ["pages/index/index", "pages/logs/logs"],
  "window": {
    "navigationBarBackgroundColor": "#ffffff",
    "navigationBarTitleText": "小码的小程序",
    "navigationBarTextStyle": "black",
    "backgroundColor": "#f8fafc"
  },
  "style": "v2",
  "lazyCodeLoading": "requiredComponents",
  "sitemapLocation": "sitemap.json"
}

"lazyCodeLoading": "requiredComponents" 表示：只注入当前页面在 usingComponents 里声明了的组件。页面多、组件多的项目，启动速度提升立竿见影。

注意

开了按需注入后，组件必须在页面的 usingComponents 里显式声明才会被注入。如果一个组件只靠全局 app.json 注册之外的途径动态使用却没声明，可能出现渲染空白。改造老项目时逐页检查一遍声明。

✅ 你应该看到： 加上配置重新编译后，功能一切正常；打开调试器 Console 无报错，日志页的自定义组件照常渲染——说明注入是「按需」而非「缺席」。

🖼️ 图片优化：最立竿见影的一刀 ​

图片通常占一个应用体积和流量的大头，按三层优化：

  1. 压缩：上传前用 TinyPNG 之类的工具压一遍，2M 的截图常常能压到 200KB
  2. 换格式：优先用 WebP，同画质体积约为 JPG 的一半（真机兼容性以官方文档为准）
  3. 懒加载：给 image 组件加 lazy-load 属性，图片进入视口附近才下载
xml
<!-- 懒加载 + 固定宽高（防止图片加载后页面跳动） -->
<image
  class="cover"
  src="https://cdn.example.com/pic-{{index}}.webp"
  lazy-load
  mode="aspectFill"
/>

🧪 体验评分面板：一键体检 ​

不知道哪里慢？让官方工具替你查。体验评分（Audits） 会模拟真实使用过程，按微信官方的最佳实践逐项检查：

  1. 打开微信开发者工具，进入你的项目
  2. 点击调试器面板里的「Audits」标签（找不到就点调试器右上角「+」号添加）
  3. 点击「运行」按钮，然后像普通用户一样操作页面：点点按钮、跳跳页面、滑滑列表
  4. 操作 20 秒左右后点击「停止」，等待报告生成

✅ 你应该看到： 面板顶部出现一个分数（满分 100），下方按「性能、体验、最佳实践」列出问题清单，每一条都能展开看到「哪里有问题 + 官方修复建议」，常见条目如「存在图片没有按需加载」「setData 数据量过大」。

注意

体验评分是「体检报告」不是「KPI」。分数不用追到满分，重点处理红色的高优先级项；每修一条，重新跑一次评分对比前后变化，这才是正确的优化节奏。

✏️ 分级练习 ​

  1. 🟢 跟做型：给 native-demo 开启 lazyCodeLoading，跑一次体验评分，把「分数 + 前三条问题」截图记在笔记里
  2. 🟡 修改型：给首页的计数按钮加 300ms 节流：连续点击时只取最后一次更新到 data（提示：用 setTimeout + 定时器标记）
  3. 🔴 创作型：做一个 50 条数据的图片列表页，完成「压缩图片 + WebP + lazy-load + 固定占位高度」全套优化，用体验评分对比优化前后的分数差

⚠️ 常见坑 ​

  • 页面越滑越卡 → 在 onPageScroll 或滚动事件里高频全量 setData → 先节流，再改成路径更新，只传真正变化的字段
  • 开启 lazyCodeLoading 后某些组件渲染空白 → 组件没在对应页面的 usingComponents 里声明，按需注入就不会加载它 → 逐页补全声明
  • 上传时提示包体积超限 → 主包超过限制（具体上限以官方文档为准）→ 图片移到 CDN、删除无用文件、把低频页面拆到分包
  • image 加了 lazy-load 却还是全部立刻加载 → 懒加载只对 page、scroll-view 内直接滚动的 image 生效 → 把图片放进可滚动容器里，并确认没有用 swiper 等特殊容器包裹
